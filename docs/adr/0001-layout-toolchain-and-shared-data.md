# ADR-0001: Package layout, toolchain and shared data

- Status: Accepted
- Date: 2026-09-25 (amended 2026-10-07 for hub ADR-0004: the patro moves to its own distribution)
- Deciders: Sanam Pakuwal

## Context

The Python port is one spoke of the NepDate family (hub ADR-0001). It must stay dependency-free,
install everywhere (including Pyodide and free-threaded builds) and give the same results as every
other port. Hub ADR-0004 requires a core unit and a separate patro unit in every port.

## Decision

1. **Two distributions in one repository, as a uv workspace:**

   | | Core | Patro |
   |---|---|---|
   | Distribution (PyPI) | decided in P0-06: `nepdate`, or `nepdate-bs` while `nepdate` is taken (`docs/competitors.md`, "Name") | `nepdate-patro` |
   | Import name | `nepdate` | `nepdate_patro` |
   | Directory | repository root: `pyproject.toml`, `src/nepdate/` | `packages/nepdate-patro/`: own `pyproject.toml`, `src/nepdate_patro/` |
   | Depends on | nothing (except `tzdata` on Windows, §4) | the core at the same minor version |

   The root `pyproject.toml` is both the core project and the workspace root
   (`[tool.uv.workspace] members = ["packages/nepdate-patro"]`). The patro project declares the
   core as `"<core-name>>=0.1,<0.2"` (moved to the next minor in every minor release) and
   `[tool.uv.sources] <core-name> = { workspace = true }`, so development uses the local core.
   `<core-name>` is the core distribution name from P0-06.
2. **Why not `nepdate.patro`:** `nepdate` is a regular package (it has `__init__.py`), so every
   `nepdate.*` module must come from the one distribution that owns that directory. A subpackage
   shipped by a second distribution would need `nepdate` to be a namespace package, which means
   no `__init__.py` and so no top-level API. The patro import name is therefore `nepdate_patro`.
3. **Python 3.11+** (`requires-python = ">=3.11"`) for both: 3.10 reaches end of life in 2026-10. CI
   tests 3.11, 3.12, 3.13, 3.14, 3.14t (free-threaded) and the 3.15 pre-release.
4. **Build and tools:** each `pyproject.toml` uses the `uv_build` backend (pure Python, no hooks);
   `uv` for the one lock file and every command; `ruff` (lint + format); `mypy --strict` as the
   type gate (`ty` may run as an extra, not as the gate while it is pre-1.0); `pytest` +
   `hypothesis`. All in the root `[dependency-groups] dev`.
5. **Runtime dependencies:** the core has none, except `tzdata; sys_platform == "win32"` so `today()`
   can load `Asia/Kathmandu` on Windows. The patro distribution depends only on the core. Both ship
   `py.typed`. The core never imports, depends on or contains anything from `nepdate_patro`.
6. **Shared data:** `shared/` is a read-only copy of the hub's `data/` and `spec/` with
   `shared/VERSION` (hub ADR-0001 §3). CI calls the hub's reusable `shared-check`; the weekly
   `shared-sync` runs `uv run python scripts/codegen.py`.
7. **Generator:** `scripts/codegen.py` (standard library only) writes `src/nepdate/_calendar.py`
   from `shared/data/calendar/` and `packages/nepdate-patro/src/nepdate_patro/_tables.py` from
   `shared/data/patro/`, each starting with `# Generated by scripts/codegen.py. DO NOT EDIT.`
   `--check` fails on drift in either file.
8. **Dev commands** are Python scripts run with `uv run`, so Windows works: `scripts/ci.py` runs every
   gate (ADR-0004).

## Consequences

- Installing the core gives one pure wheel (`py3-none-any`) on every platform with no event strings
  in it. Installing `nepdate-patro` pulls in the matching core.
- Nothing is parsed at import time. `nepdate_patro` builds its per-day objects from generated
  constants when it is imported, in about 2.4 ms (ADR-0002 §6).
- Two PyPI projects, so two trusted publishers on PyPI and two on TestPyPI (ADR-0005).
